# ADR-0012 Old addresses are answered in a request-level proxy from a generated map

- Status: Accepted (2026-11-11, main agent; the owner may override)
- Context: MIG-02 asks that every old university address returns 301 or an explicit 410. The route map (`scripts/import/data/route_map.csv`, 1,613 rows) has three kinds of row: 1,542 move to a new path, 5 are dead links on the old site, and 66 keep the same address. Every old address and every target ends in a trailing slash, while the site's addresses have none. The Redirects collection already installed by the Payload plugin is applied inside page renders by `PayloadRedirects`, which uses the framework's `redirect()` (a temporary 307 in a server component), cannot return 410, and only runs for routes that reach that component. Next's own `redirects` in `next.config` gives 308, not 301, and 1,542 static entries would be rebuilt into every deployment.
- Decision: `src/proxy.ts` answers old addresses before any page renders, from `src/legacy/routeMap.generated.json`, which `pnpm routemap:build` writes from the CSV. A mapped address answers a real 301 to its new path, or 410 with `x-robots-tag: noindex`, with or without a trailing slash. `skipTrailingSlashRedirect` is on in `next.config.ts` and the proxy does the slash redirect itself (308, same as the framework's), so an old address ending in "/" is one hop, not a slash redirect followed by a 301. The 5 dead links answer 410 (the old site already returned 404 for them); the owner may choose a redirect to a parent instead. The 66 same-address rows are not redirects (a redirect to themselves would loop). The Redirects collection stays as the editors' place for redirects added after cutover; the two do not overlap because the proxy runs first.
- Alternatives considered: (a) load the CSV into the Redirects collection (the earlier plan): 307 and no 410, and each request reads the collection; (b) `redirects` in `next.config`: 308 and 1,542 entries rebuilt on every deploy; (c) host-level redirects at the university's web server: not available on the demo and not portable (MIG-03).
- Evidence: unit tests over the real CSV (no repeated address, no chain, no reserved-route collision, every row accounted for, JSON in sync, three mutation checks caught); an e2e run against a production build requesting all 1,613 old addresses as the old site wrote them (1,542 answer 301 to the right path and that path does not redirect again, 5 answer 410, 66 are never 301 or 410).
- Consequences: one new file convention (`proxy.ts`) and a 190 KB generated JSON in the proxy bundle; editing the CSV needs `pnpm routemap:build` (a test fails if it is forgotten). Three in, two out (rule 9): it lets us drop the planned CSV loader and the per-request redirect lookup for these addresses.
- Cost of reversal: low. Delete `proxy.ts` and the config line; the CSV and the tests remain.
- Reversal trigger: the university moves the old addresses to its own web-server redirects, or the map grows past what a bundled JSON handles comfortably (several tens of thousands of rows).
- Owner: main agent.
- Review date: at cutover rehearsal (MIG-06).
- Prediction: P4-b in `docs/predictions.md`.
