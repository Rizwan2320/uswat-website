# ADR-0026 Sample content is seeded by the preview build, not copied in by hand

- Status: Proposed (main agent, 2026-11-19). Not yet in use; the code comes from agent 4 and is reviewed by the main agent.
- Context: The owner will test the CMS on the Neon `previews` branch with dummy content only. The sandbox the agents work in cannot reach Neon (DNS fails; HTTPS to Neon is refused by the proxy), and the seed scripts refuse any hosted database on purpose (`assertLocalDatabase`). The only route in from the sandbox is the database tool, which passes SQL through the conversation.
- Decision: A preview build may run the Sample accounts and seeds against the `previews` database when ALL of these are true: `VERCEL_ENV` is `preview`; `SEED_SAMPLE_ON_PREVIEW` is `true` (set only in Vercel's Preview scope, and switched on only when needed); the database host equals `SEED_ALLOWED_DB_HOST` (the `previews` branch host). A production build never runs it, even if the flag is set by mistake, because the host check fails. `assertLocalDatabase` is unchanged for every other caller. The seeds are idempotent, never touch an existing record or user, and a failure never fails the build. Test-account passwords come from three Preview-scope variables and are never printed or committed.
- Alternatives considered: (1) Paste a data-only SQL file through the database tool. Tried on the organisation seeds alone: 206 rows is about 92 KB, one circular foreign key needs the constraints dropped and re-added in the same transaction, and copying that much text by hand risks silent errors; the full pack would be several times larger. (2) A GitHub Actions job holding a Neon connection string as a repository secret. It copies the database credential to a third place. (3) Loosen `assertLocalDatabase` to allow Neon. Rejected: it removes the guard that protects production.
- Evidence: Drill TR-b in `docs/predictions.md` (the dry run on a fresh migrated database: counts and all 339 foreign keys matched; the first two attempts failed on foreign keys and on missing version rows). The `previews` database was checked on 2026-11-19: 9 migrations, empty content tables, one existing user (`cms-tester@example.test`).
- Consequences: Each preview build spends about 10 seconds on a no-op seed after the first run. All previews share one database, so a seed run by one branch is seen by the others. Image files are not persisted by this route (see slice 3t). Sample rows reaching production is the main risk; the three locks, the Sample source key (`sample.invalid`) and the Sample pill on screen are the protection.
- Cost of reversal: Remove the build-script line and the Preview variables; Sample rows stay in `previews` and can be deleted by their source key.
- Reversal trigger: any Sample row found in production; a preview build failing because of the seed; the owner objecting.
- Owner: main agent. Decision by the owner: pending (the owner said on 2026-11-19 to decide, so this goes ahead as Proposed until they object).
- Review date: after the first end-to-end test.
