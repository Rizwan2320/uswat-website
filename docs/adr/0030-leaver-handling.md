# ADR-0030 Leaver handling: account, roles and public page end together

- Status: Proposed (owner instruction 2026-11-28, "decide yourself"; the public-page part needs the lead)
- Context: Addendum C section 5.6 and FP-07 say that on departure the account ends the same day and the public profile becomes read-only "former faculty" or "emeritus", with the address kept and contact details removed. Before this, the only way to end an account was an operator command, which did nothing to the public page, so a person who had left kept their email and office on the website.
- Decision: The Registrar (the existing Verifier role) gets a "Mark as left" action with an outcome (former or emeritus), a source document and a ticked confirmation, behind the same fresh passkey check as other changes. In one transaction it sets the status to left (sessions deleted, delegations revoked, by the same function the operator command now uses), removes the person's reviewer, head and Registrar roles, and writes one insert-only row to `account_departure`. After the commit the portal sends the existing signed bridge message with a new optional `departure` value; the site sets `facultyStatus`, clears email, office location and office hours, and keeps name, biography, photo and works. The public page also hides all contact details for any non-current person, whatever the record holds.
- Three-in, two-out (rule 9): no dependency. It lets us remove the manual two-step (operator command, then someone editing the CMS record by hand) and the old "contact details may stay on a former page" gap.
- Alternatives: leave it to the CMS editor to change the status (rejected: nothing ends the account, easy to forget, no log); delete the page (rejected: breaks addresses and citations, spec says keep them); a separate message type (rejected: one allow-listed contract is easier to keep safe).
- Consequences: Migration 0019 on the portal database (one table, reversible). People write by the bridge now also changes status and clears three fields, only for a departure. A head or reviewer who leaves takes the role with them, so a department can be left without a head (shown on screen and in the log). Reinstating an account stays an operator command and does not change the public page. How long portal data is kept after leaving is a university decision, not made here.
- Cost of reversal: low (drop the table, remove the card and the optional message value; the receiver ignores unknown values by refusing them).
- Reversal trigger: a Registrar marks the wrong person and the university wants a self-service way back; the chair access review is built and wants to share this log.
