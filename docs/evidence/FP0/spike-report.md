# Spike S-2 report: can Better Auth carry the faculty portal's sign-in?

Date: 2026-11-10. Branch `p3/faculty-portal-spec`. Brief: `docs/briefs/fp0-faculty-portal.md`. Spec: Addendum C sections 5, 8 and 9 (project doc `addendum 3.txt`). Predictions: `docs/predictions.md` FP0-a, FP0-b, FP0-d (reconciled below).

## What was run, and what was not
Run: a throwaway Node server (`scripts/server.mjs`) using `better-auth` 1.7.19 with `@better-auth/passkey` 1.7.19 and its two-factor plugin, on a local PostgreSQL 16.15 (port 5544, database `fp0`, tables in a separate schema `identity`). Chromium driven by Playwright 1.63.0 with a CDP virtual authenticator (no hardware). The whole script ran twice: once with the passkey plugin's user verification set to `required`, once with the library default. Raw results: `results/results-required.json`, `results/results-default.json`. To reproduce: `scripts/run.sh required 3010` and `scripts/run.sh default 3011` (needs the local PostgreSQL above).

**Not run:** the library inside this repository's Next.js 16 and Payload 3.93 app (the spike used a plain Node HTTP server, so "runs beside Payload" is unproven); prediction FP0-d (whether Payload's migrate tools ignore a second schema); a Payload custom-strategy alternative (FP0-b); OIDC federation (AUTH-08); idle-timeout behaviour (SES-04); step-up (AUTH-09); delegation; rate limiting and alerts (ABU); the breached-password check (the library's plugin calls an outside host, and this sandbox has no route to it); real devices or real phones; load. Neon was not touched.

## Findings that change the plan
1. **User verification is not enforced by default.** The server config must set `userVerification: "required"`. A test that asserts UV=0 is rejected has to stay in CI (FPR-01), or a library upgrade could silently weaken it.
2. **No mandatory second factor out of the box (AUTH-01).** A user with only a password gets a full session at sign-up and at sign-in (B1, B2). We need our own gate: until a passkey or TOTP is enrolled, the session may reach only the enrolment screens. Designed, not built or tested.
3. **TOTP replay is accepted (AUTH-04).** Needs our own guard: store the last accepted time step per account and reject any code at or below it. Designed, not built or tested.
4. **Recovery codes are encrypted, not hashed (AUTH-05).** Either accept encryption with a key held outside the database as the documented deviation (a waiver by the owner), or replace the library's backup-code check with our own hashed one. The second option means writing code the spec wanted to avoid (ADR 0023: no hand-rolled cryptography; hashing a random code with SHA-256 is not custom cryptography, but it is our code).
5. **Cookie naming needs a non-default setup.** With `useSecureCookies: true` the library always prefixes `__Secure-` and the name becomes `__Secure-__Host-portal.session_token`, which loses the `__Host-` guarantees. Setting `useSecureCookies: false` plus `defaultCookieAttributes.secure = true` gives the right name. Source: `better-auth/dist/cookies/index.mjs`.
6. **Session token is stored raw** (32 characters in the `token` column), where Addendum C's data model has `idHash`. The browser cookie is longer (77 characters, so it carries a signature, inferred from the length, not decoded), which means a database leak alone should not be enough to forge a session. Deviation to accept or fix. The library's cookie cache must stay off, or revocation would not be immediate.
7. **Session lifetime.** The library has an absolute lifetime (`expiresIn`); the spec's 30-minute idle limit (SES-04) is not a native setting. Not tested.
8. **Cross-origin POST refused (SES-06: 403) and the sign-in response is identical for an unknown email and a wrong password (AUTH-10, status and body; timing was not compared).** Password length 15 enforced with no composition rules (AUTH-03); the breached-password blocklist was not tested.

## Reconciliation of predictions
- **FP0-a** predicted (60%) that the passkey UV test, the UV=0 rejection and the TOTP replay rejection would all pass from library defaults. Actual: **0 of the 3 passed at defaults** (UV=0 accepted; replay accepted); with one setting changed, UV passes; replay still fails. Snag 1 happened as predicted. Snag 2 (library creating tables outside Payload's migrations) did not: schema comes out as SQL we control, provided nobody runs the library's own `migrate` command. Snag 3 happened in another form: the cookie name, not `Secure` on localhost.
- **FP0-b** (Payload custom strategy would not be chosen unless Better Auth failed on schema ownership): Better Auth did not fail there. The alternative was not run, so nothing was compared.
- **FP0-d:** not run.
- **FP0-c** (G-FP0 ends as a no-go) is still open: it depends on the Must list and on the owner, not on this spike.

## Recommendation, auth side only (the gate decision also needs the Must-list status and the owner's approval)
Better Auth is viable for passkeys with user verification, server-side sessions and revocation. It is not enough on its own: three controls the spec calls non-negotiable (enrolment gate, TOTP replay guard, hashed or waived recovery codes) need our own code, and "runs inside the Next.js 16 and Payload app" is still unproven. If the slice goes ahead, the first half day is: run the library inside the app on its own route, build the three controls with tests written first, and run FP0-d. If that does not hold, the fallback stays the specification plus this report.
