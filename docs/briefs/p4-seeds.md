# Brief: Sample organisation seeds, agent 4, 2026-11-13

- **Objective.** Give the templates (T3 department, T4 programme, T7 faculty group, T8 person and the directory lists) real rows to render, using invented Sample data, because the data pack is absent and the owner said to use dummy data ("we will use the dummy data"). Every row is labelled Sample, so nothing here is an institutional fact (CLAUDE.md rule 3).
- **Paths touched.** `scripts/import/seeds/**` (data and applier), `apps/web/scripts/seed-sample.ts` (thin entry, same place as `import.ts`), `apps/web/package.json` (one script, `seed:sample`), tests under `apps/web/tests/`, `docs/predictions.md`, `docs/STATUS.md`. Nothing under `src/collections`, `src/governance` or `src/migrations`.
- **What is seeded.** 3 faculty groups, 2 campuses, 4 offices, 10 people, 8 departments, 14 programmes. Every name starts with "Sample". Contact data uses `sample.invalid` only; the one Sample person with a public email is there so a template can show the "public" case; every other email is hidden by default. No campus address (the Campuses collection says addresses are disputed and decided by the Registrar).
- **Key.** `governance.source = https://sample.invalid/seed/<collection>/<slug>`. A re-run finds records by that key and creates nothing. The host `sample.invalid` is also how the site can show a "Sample" pill later.
- **Publishing.** Seeds are created as drafts, linked while still drafts (person to department, department head), then moved draft, in review, approved and verified, published by a `platformAdmin` actor. "Verified" here means "checked as Sample data". It is not a fact check, and the on-screen Sample label stays until the owner replaces the rows with real, sourced ones.
- **Risks.**
  1. Writing to a hosted database. `assertLocalDatabase` (importer) is called first; the entry refuses anything but this machine. Putting Sample rows on a demo or preview database is the main agent's decision, not made here.
  2. Dummy rows reaching production by accident. The Sample name prefix, the `sample.invalid` source and the unit test that checks both make them easy to find and remove.
  3. Editing a published record on re-run. A published record is never touched; the seeds only link and publish records that are still drafts.
  4. The acting admin. If `SEED_ADMIN_EMAIL` names an existing user it is used; otherwise, on the local database only, a throwaway `platformAdmin` is created with a random password that is never printed or stored.
- **Tests.** Unit: data integrity (unique names and slugs, every reference resolves, every name starts with "Sample", no address outside `sample.invalid`). Integration on local PostgreSQL: first run creates everything and publishes it; second run creates 0 and adds no version rows; relations intact; an anonymous read sees the published rows; a hidden email is not returned and the one public email is.
- **Gate.** Two runs, second one a no-op; anonymous reads show only published Sample rows with working relations.
